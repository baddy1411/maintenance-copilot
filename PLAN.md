# Maintenance Copilot: From-Scratch Build Plan

Oct 28, 2026 · @Badrish Madapuji Srinivasan

We build it from scratch, phase by phase, into a production-grade applied AI project: about 10 weeks at 2 to 3 hrs/day. Every phase ends with a gate, and nothing moves on until its exit checks pass with evidence.

## How to use this plan

1. Create a new public GitHub repo (e.g. `maintenance-copilot`) and clone it into a fresh folder.
2. Save this file as `PLAN.md` at the repo root.
3. Open Claude Code in the repo. Switch model with `/model` as the table below says.
4. One phase per session. Paste that phase's prompt. Run `/clear` between phases; state lives in `PLAN.md`, `docs/` and `docs/PROGRESS.md`, not in chat history.
5. After each phase: commit, tag (`phase-N`), update `docs/PROGRESS.md`.

## Rules for Claude Code (apply in every phase)

- **Evidence over claims.** Never say something works without running it and showing the output. Anything not verified is marked UNVERIFIED.
- **No guessing.** Don't guess install commands, library APIs or cloud settings. Read the current docs first.
- **Thin slices.** Get one path working end to end first, then deepen it. No feature lands without a test.
- **Stop at every gate.** Summarise what was done, show test and eval results, list open questions, wait for my approval.
- **Ask before spending money.** Cloud resources or paid LLM loops need an estimated cost and a hard cap first.
- **Secrets never in code, logs or traces.**
- **Every change ships with tests.**
- **Design reviews use the Elephant-Goldfish Model** (`github.com/google/elephant-goldfish-model`): the Elephant drafts with full context, fresh-context Goldfish reviewers attack the draft. Install it per its README; if that fails, replicate the pattern with fresh subagents.

## Runtime model: OpenRouter

No local model. Every LLM call goes through **OpenRouter** via one OpenAI-compatible provider layer. Base URL, key and model IDs come from config only, so a company can point it at its own OpenAI-compatible endpoint (for example Azure OpenAI or a self-hosted server) with no code changes.

- **Model chosen by evals in Phase 3:** compare 2 to 3 models on OpenRouter, weighing answer quality, tool calling, structured output, latency and cost.
- **Key rules:** key only in `.env` / Secrets Manager, never committed; hard credit limit set on the key; no free-tier models for evals (rate limits make results inconsistent); pin exact model IDs, and the upstream provider where possible, so results are reproducible; log tokens and cost per request.
- **Verify tool calling** for each chosen model before building on it, since support varies by model and upstream provider.
- **Safeguards:** JSON-schema constrained output, validation with bounded retries, timeouts, and a fallback model if the primary fails.
- **Embeddings and reranker** also via API; provider chosen in a Phase 1 ADR.
- **Data flow:** manuals and questions are sent to a third-party API. State this plainly in the system card and security docs.

## Phase 0: Scope and spike (week 1)

**Model: Opus 5.5.** Goal: lock the scope and prove the riskiest pieces work before building anything properly.

1. **Scope:** write `docs/SCOPE.md`: users (maintenance technician, supervisor), the three core paths (cited question answering over manuals and fault logs; document ingestion; an agent that troubleshoots and drafts a work order with human approval), and what is out of scope.
2. **Data:** choose public equipment manuals whose licences allow use, plus synthetic fault logs, asset lists and work-order history generated by seed scripts. Record sources and licences in `docs/DATA.md`.
3. **Agent sketch:** the LangGraph flow (plan, retrieve, read-only SQL, diagnose, draft work order, pause for approval) with the tool list and Pydantic schemas.
4. **Spike:** throwaway code in `spikes/` proving three things: a candidate model on OpenRouter calls your tools reliably, retrieval over a few manuals returns the right passages, and a LangGraph interrupt for human approval works. Findings go in `docs/SPIKE.md`.
5. **Model shortlist:** 2 to 3 OpenRouter candidates for the Phase 3 comparison.

**Exit gate:** `SCOPE.md` and `DATA.md` approved; the spike shows tool calling and the approval interrupt working. Until Phase 9, my CV lists this project only as in progress.

## Phase 1: Design (week 1 to 2)

**Model: Opus 5.5.** Goal: an approved target architecture, written down, before any new code.

1. **Elephant draft.** From `PLAN.md`, `SCOPE.md` and `SPIKE.md`, write `docs/DESIGN.md`: components, data flow for the three main paths (question answering, document ingestion, work-order creation), and failure handling on each path.
2. **Service-level targets.** Write numbers into the design: p95 latency for an answer, availability goal, cost-per-query budget, minimum eval scores. Later phases are judged against these.
3. **Starting architecture to challenge** (not final):
   - Async FastAPI API with streaming answers
   - LangGraph agent service
   - Ingestion worker fed by a queue (Redis-based locally, SQS on AWS)
   - Postgres + pgvector, Redis for cache and rate limits
   - MCP server exposing the tools
   - React frontend
   - OpenTelemetry collector
   - AWS deployment through Terraform
4. **Decision records.** One short file per major choice in `docs/adr/` (queue, hosting, eval tooling, observability backend): options, choice, why, trade-off.
5. **Goldfish reviews, three lenses, fresh context each:** security, cost and scale, operations and maintainability. Elephant revises and logs what changed and why.
6. **Backlog.** Turn the design into GitHub issues grouped by phase.

**Exit gate:** I approve `DESIGN.md`; ADRs exist; issues are created.

## Phase 2: Foundation hardening (week 2)

**Model: Sonnet 5.5.** Goal: the core paths work end to end, and a stranger can run the app with one command. This is the heaviest phase now that we're building from scratch.

1. **Core build first:** ingestion (parse, chunk, embed into pgvector), cited question answering, and the LangGraph agent with Pydantic-validated tools (manual search, read-only SQL, work-order drafting), idempotent work orders and a human-approval step, each with tests.
2. **Repo hygiene:** `uv` with a lockfile, pre-commit (ruff, mypy, eslint, prettier), a `Makefile` with `make up`, `make test`, `make eval`, `make lint`.
3. **Config:** pydantic-settings, `.env.example`, no secrets in the repo, gitleaks in CI.
4. **Async end to end:** async database driver, async LLM client, no blocking calls in the request path.
5. **Streaming:** answers stream to React over server-sent events; citations arrive at the end of the stream.
6. **Local stack:** Docker Compose brings up API, worker, Postgres, Redis and frontend together, with seeded sample manuals and fault logs.
7. **Tests:** unit tests, integration tests against real Postgres via testcontainers, contract tests for every tool; a coverage threshold enforced in CI.

**Exit gate:** in a clean container, fresh clone to working app with `make up` in under 10 minutes; CI green.

**Prompt to paste:**

Then repo hygiene, config, async, streaming, Compose stack and tests. Prove the exit gate by running a fresh clone in a clean container and showing the output. Stop at the gate.

## Phase 3: Evaluation harness (week 3)

**Model: Opus 5.5 to design, Sonnet 5.5 to build.** Goal: quality is measured on every change, and a bad change cannot merge. Evals are the skill hiring guides call the 2026 differentiator.

1. **Golden dataset:** grow the labelled set to roughly 100 to 200 questions with evidence IDs, versioned in `evals/datasets/`. Cover direct lookups, multi-document questions, fault-log reasoning, unanswerable questions, injection attempts and SQL questions.
2. **Retrieval metrics:** recall@k, MRR, nDCG against the evidence labels.
3. **Answer metrics:** groundedness, citation correctness (does the cited chunk actually support the sentence), correctness against a reference, correct refusal on unanswerables.
4. **LLM judge:** a written rubric; calibrate it against about 30 examples I label by hand and report agreement. An uncalibrated judge is not trusted.
5. **Agent metrics:** right tool chosen, valid arguments, task success on work-order flows, steps and cost per task.
6. **Tooling:** compare writing a light pytest harness vs an open-source tool (e.g. Ragas, DeepEval, promptfoo); check their current state and record the choice in an ADR.
7. **CI gate:** a cheap smoke eval (about 20 cases, budget-capped) on every pull request, the full eval on demand or nightly. The PR fails if a metric drops past a threshold vs the main branch; results posted as a PR comment.
8. **Experiments:** compare chunk sizes, hybrid search (BM25 + vectors), reranker on vs off, and two models. Record numbers in `docs/experiments.md`; these make great interview stories.

**Exit gate:** baseline eval report exists, and a demo PR that deliberately worsens a prompt gets blocked by CI.

## Phase 4: Cost management (week 4)

**Model: Sonnet 5.5, Opus 5.5 for the routing policy.** Goal: a measured drop in cost per query with no meaningful quality loss.

1. **Cost accounting first:** record input and output tokens, cache hits, model used and dollar cost per request, per user and per agent run. You can't optimise what you don't measure.
2. **Provider prompt caching** for the long static parts of prompts (system prompt, tool definitions). Check the provider's current docs for how it works and is priced.
3. **Semantic cache:** reuse answers for near-duplicate questions; tune the similarity threshold on the eval set; invalidate entries when the underlying documents change.
4. **Model routing:** a cheap model for simple lookups and classification, a strong model for multi-step diagnosis. Evaluate the router with a quality-vs-cost table.
5. **Context budget:** use reranking to send fewer, better chunks; cap tokens per request.
6. **Limits:** daily token budget per user, max agent steps per run, and a spend circuit breaker that degrades gracefully.
7. **Ingestion:** batch embedding calls; skip re-embedding unchanged documents using content hashes.

**Exit gate:** a before/after table on the eval set showing cost per query, p95 latency and quality score.

**Prompt to paste:**

## Phase 5: Guardrails and security (week 4 to 5)

**Model: Opus 5.5 for the threat model and final review, Sonnet 5.5 to build.** Goal: a written threat model, layered defences and a measured attack success rate.

1. **Threat model** in `docs/security/THREAT_MODEL.md`, using STRIDE plus the current OWASP Top 10 for LLM applications (check the latest version).
2. **Input guardrails:** injection detection on user input and on retrieved documents (a poisoned manual is a real attack path), plus length and rate limits.
3. **Output guardrails:** schema validation, citations required, PII redaction, and a domain safety rule: requests to bypass safety interlocks or lockout/tagout get refused and escalated. That's a strong industrial touch for interviews.
4. **Tool security:** least-privilege database role (read-only at the database level, statement timeout, row limits), allowlisted tables, human approval for every write, and an audit log of all tool calls and approvals.
5. **Access control:** OIDC/JWT login, roles (technician, supervisor, admin), and document-level permissions enforced inside retrieval through metadata filters, so users never retrieve what they can't see.
6. **API hardening:** rate limiting, strict CORS, security headers, input validation.
7. **Supply chain:** pip-audit, npm audit, Trivy image scan, Dependabot, gitleaks, an SBOM.
8. **Red-team suite in CI:** automated attacks (direct and indirect injection, data exfiltration, privilege escalation, jailbreaks). Report attack success rate before vs after.

**Exit gate:** threat model done, red-team report with numbers, no open high-severity findings.

**Prompt to paste:**

## Phase 6: MCP server (week 5)

**Model: Sonnet 5.5.** Goal: any MCP-capable agent (Claude Code, Claude Desktop, Cursor) can use the copilot's tools safely.

1. **Expose the tools** with the official MCP Python SDK: manual search, read-only fault-log queries, asset info, and work-order drafting that requires approval. Check the current spec version and recommended transport first.
2. **No bypass:** the MCP path uses the same auth, guardrails, limits and audit log as the API.
3. **One tool layer:** the LangGraph agent and the MCP server share a single tool implementation; record the design in an ADR.
4. **Tests:** integration tests plus verification with the MCP Inspector.
5. **Demo:** connect from Claude Desktop or Claude Code and record a short GIF diagnosing a fault from a real-looking log.

**Exit gate:** tests pass, the Inspector check is clean, the demo GIF is recorded.

**Prompt to paste:**

## Phase 7: Observability (week 6)

**Model: Sonnet 5.5.** Goal: any request can be traced end to end, and cost, latency and quality are visible on one dashboard.

1. **OpenTelemetry tracing** across API, agent, tools, LLM calls and database, following the current GenAI semantic conventions (check the latest).
2. **Backend:** self-hosted Langfuse or a Grafana stack (Tempo, Loki, Prometheus). Pick one in an ADR; stay on free or self-hosted options.
3. **Dashboard:** request rate, p50/p95 latency, error rate, tokens, cost per day, cache hit rate, router split, guardrail trigger rate, eval scores over time.
4. **Online evaluation:** sample live traces and score them with the judge asynchronously; thumbs up/down feedback linked to traces.
5. **Alerts:** error-rate spike, spend spike, latency target breached.
6. **Privacy:** prompts and outputs in traces go through PII redaction.

**Exit gate:** screenshot-ready dashboard, and a deliberately injected failure can be traced to its cause in under 2 minutes.

**Prompt to paste:**

> Read `PLAN.md` and `DESIGN.md`. Do Phase 7 only. Instrument the full path with OpenTelemetry, set up the chosen backend, the dashboard, online evaluation and alerts. Then inject a failure and show me how to trace it. Stop at the gate.

## Phase 8: Scale and deploy (week 7)

**Model: Opus 5.5 to design and read load tests, Sonnet 5.5 for Terraform.** Goal: one-command, reproducible cloud deployment with load-test numbers to back up scalability claims.

1. **Infrastructure as code (Terraform, AWS):** networking, container hosting (ECS Fargate or App Runner; decide in an ADR), RDS Postgres with pgvector, Redis, SQS, Secrets Manager, load balancer with HTTPS, logs.
2. **Cost safety:** a monthly cost estimate before applying anything, an AWS budget alarm, scale-to-minimum settings and a `make destroy` teardown.
3. **Continuous deployment:** GitHub Actions builds, scans, pushes to ECR and deploys via OIDC (no long-lived AWS keys); staging and production; migrations as a deploy step; one-click rollback.
4. **Scaling design:** stateless API with horizontal autoscaling, workers scaled on queue depth, database connection pooling, a tuned HNSW index for pgvector.
5. **Load test with Locust or k6:** ramp concurrent users; record requests per second, p95 latency, error rate and cost per 1,000 queries. Find the first bottleneck, fix it, re-test, and publish both runs.
6. **Resilience:** fallback LLM provider; graceful degradation that returns the retrieved documents when generation is down; timeouts everywhere.

**Exit gate:** deploy from scratch with one command, load-test report in `docs/`, and a results report, then a full teardown with make destroy. No live demo is kept running.

## Phase 8b: Company-ready packaging (week 8)

**Model: Sonnet 5.5, Opus 5.5 for the final review.** Goal: a company can deploy it in their own environment from the docs alone, in their own cloud or data centre, pointed at their own LLM endpoint.

1. **Three deployment targets:** Docker Compose for a single server, a Helm chart for Kubernetes, and the Terraform module for AWS, all parameterised.
2. **Bring your own LLM endpoint:** OpenRouter by default; any OpenAI-compatible endpoint works by setting base URL, key and model ID. Document exactly what data leaves the network.
3. **Configuration reference:** every setting documented with defaults; LLM provider, database, auth provider and storage swappable by config.
4. **Bring your own data:** documented import path for a company's own manuals, fault logs and asset lists, with sample data and seed scripts.
5. **Operator docs:** install guide, upgrade guide, backup and restore, secret rotation, scaling guide, troubleshooting runbook, security hardening checklist.
6. **Releases:** semantic versioning, a changelog, signed container images on GitHub Container Registry, and a licence choice.

**Exit gate:** in a clean VM, following only the docs, the stack installs, imports sample data and answers questions on both Compose and Kubernetes.
